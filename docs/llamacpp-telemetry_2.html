Where this comes from. A collector on the server samples /metrics and /slots every 5s into SQLite and serves this window back. Because the counters are monotonic, any two samples difference into exact throughput for the span between them, so long windows stay accurate however coarsely they are bucketed. Generation is measured from slot progress per bucket; prefill is differenced from the prompt counters. Breaks in the line are server restarts, and a red tick marks a bucket where the server was unreachable.

Why the counters looked idle. The server commits tokens_predicted_total and its timing only when a slot releases, at the end of a request. A reasoning model can decode for a long time before that happens, so the counters sit flat for the whole stream and then jump at once. Thinking tokens are ordinary decoded tokens, so they are included in that jump. The live figures above come from each slot's n_decoded and n_prompt_tokens_processed, which move token by token.

The gauges are shown but never used. prompt_tokens_seconds and predicted_tokens_seconds divide lifetime tokens by lifetime compute seconds, and nothing resets that accumulator, so both settle into an all-time average. The "on completion" figures on this page come from differencing the counters between polls, which gives per-request speed as each request lands.
